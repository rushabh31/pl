PromptLab

Oct 21, 2026 · @Rushabh Patel

PromptLab lets teams test, refine and optimize the prompts inside ADK and LangGraph workflows that run as backend services, on real data and with statistically sound results. It starts with testing prompts inside running workflows, exactly as the workflows run them, then adds experimentation on small datasets, then sign-in, approvals and advanced features, without changing any service’s API contract.

Key decisions#

  • ADK and LangGraph first, through one small SDK with framework adapters; LangChain, DeepAgents and others follow. Built for thousands of workflows.
  • Business users edit, test and save a workflow’s prompts themselves; each run executes the workflow’s own code, including its retrieval, memory and tools.
  • Three phases: prompt testing that works first, then experimentation on small datasets from the read replica or entered by hand (no train, validation or test split), then sign-in, approvals and other advanced features. Built on your own PostgreSQL.
  • Workflows write to production PostgreSQL, so every test run uses a read-only test deployment enforced in the database.
  • From Phase 3, leads approve changes to protected environments; before that, production changes need explicit confirmation and PromptLab runs on a trusted network.
  • Services keep their own API contracts; PromptLab adapts with a declarative adapter.

Roadmap at a glance#

  1. Phase 1, prompt testing: connect a workflow with the SDK, see its prompts on a map, edit, run exactly as the workflow runs (prompt, node or whole workflow), compare old and new, save and activate without a deploy. No experiments, no sign-in.
  2. Phase 2, experimentation: input and output formats identified from the workflow, small datasets (10 to 20 rows) from the read replica or typed and pasted by hand, no splits, every row run several times and compared old beside new, ratings, checks and judges, change sets, LangChain and DeepAgents.
  3. Phase 3, advanced: OIDC sign-in, roles, approvals, audit, replay and FORK, CI, optimization, rollout, full scale.

PromptLab: Backend Architecture & Design Proposal

A production, multi-tenant platform to test, refine and optimize prompts inside real AI workflows · 20 October 2026 · Sources are listed in section 20.

1. Executive summary#

Recommendation: build PromptLab as a build system and experimentation platform for AI programs, not as a prompt playground. Every workflow, whatever framework it uses, is a program with text parameters. PromptLab intercepts it at the two boundaries every framework shares, the model call and the data read. It memoizes every call by content, and it turns prompt testing into incremental, statistically paired recomputation on real data.

The problem. A workflow’s accuracy comes from the whole flow: what was retrieved, what a tool returned, what an upstream prompt produced. A playground that sends one prompt and a sample input to a model tests a fiction. Langfuse’s documentation draws exactly this line: its UI experiments run a prompt and model directly, while SDK experiments run your code and therefore exercise your real retrieval and tool logic.

Why the boundaries matter. There are dozens of agent frameworks, and new ones every quarter. All of them end in a request to a handful of model SDKs or a model gateway, and all of them read data through a handful of client libraries (HTTP, SQL, vector stores, MCP). A request to the model already carries the system prompt, messages, tool descriptions and parameters, so steering at that boundary works the same for ADK, LangGraph, CrewAI and hand-rolled code. Framework-specific code shrinks to optional extras: names, templates and native checkpoints.

# Idea What it gives you
1 Steer at the model boundary One interceptor per model SDK, or a gateway, edits system prompts, tool descriptions and parameters in any framework
2 Capture at the data boundary OpenTelemetry auto-instrumentation for HTTP, database, vector-store and MCP clients, extended to record payloads, freezes what the flow read. No decorators needed
3 Memoize every call A content-addressed cache of model and data calls. Fork-from-step then emerges in any framework, even inside agent loops: unchanged calls hit the cache, and the first changed call and everything after it run live
4 Common random numbers Variants share identical upstream samples, so a paired difference isolates the prompt change and fewer items are needed
5 Prompts are runtime configuration Resolution follows OpenFeature semantics (evaluation context, variants, targeting) with an OFREP-compatible endpoint, so offline experiments and production canaries use one mechanism
6 Production traces are datasets Any captured production run can be re-executed with new parameters on exactly the context production saw
7 Test cases beyond input and output Scenarios with simulated users, metamorphic groups and trajectories, with pass^k reliability
8 One narrow waist, negotiated by capability One canonical workflow model and run protocol, with features enabled by what each runner declares
9 Statistical honesty Paired designs, intervals, calibrated judges, gated promotion

Build vs. adopt. Reuse OpenTelemetry and OpenInference for traces, a durable-execution engine for orchestration, ClickHouse for spans and scores, and the open-source gepa library for optimization. Build the differentiators: interception planes, the memo cache, the narrow waist and statistically gated promotion. Section 17 gives a phased roadmap.

About the scale question. It asks how much load PromptLab itself will carry, which decides when an analytics database is worth adding. Three numbers matter:

  • Users and workflows: how many teams and services will run tests.
  • Runs at once: an experiment of 200 items × 3 variants × 3 repetitions is 1,800 runs, and several experiments may overlap.
  • Steps per run: every model call, database query and tool call is recorded as one span; an ADK agent typically produces somewhere between a handful and a few dozen.

Postgres alone is the right start. As a planning estimate to confirm with a load test, move spans to ClickHouse when trace queries take more than a few seconds or span volume passes roughly 50 million a month.

2. What the research says, and what we do about it#

Finding (as of Oct 2026) Design consequence
OpenTelemetry’s GenAI conventions define spans for model calls, agents (create_agent, invoke_agent, invoke_workflow, plan, execute_tool) and MCP, plus a gen_ai.evaluation.result event. They moved to a dedicated repository in June 2026. Most sources still label them Development status; one source claims they are stable. Use OTLP with GenAI attributes as the trace format, pin the convention version per span batch, isolate the mapping in one module, and keep our own attributes under promptlab.*. Verify stability before pinning.
OTel spans carry timing and metadata by default; prompt and completion content is opt-in. Experiments need content, so the SDK enables content capture for experiment runs only, with redaction inside the customer’s plane.
GEPA (ICLR 2026 oral) evolves the text components of an arbitrary system by reflecting on full execution traces and textual feedback, keeping a Pareto frontier of candidates. Its adapter interface is evaluate(batch, candidate as a dict of component texts, capture_traces) plus make_reflective_dataset. It ships inside DSPy and MLflow. Our overlay is a GEPA candidate, the Runner Protocol is evaluate(), and traces feed reflection. GEPA is the default optimizer.
MLflow’s optimize_prompts (3.5+) wraps GEPA and supports multi-prompt optimization, but the app must load its prompts through the MLflow registry. That is the integration gap. Decorators make hard-coded prompts addressable so existing code works with minimal edits.
Braintrust remote evals run on your infrastructure while its playground triggers runs, sends parameters and shows results. Langfuse offers webhook-triggered SDK experiments. Confirms the callback model. We add pull-based runners (no inbound ports), several prompts per overlay, and strict modes.
Microsoft’s Agent Lightning separates agent, tracer, store and algorithm. It collects prompts, tool calls and rewards as spans, feeds improved prompt templates back, and uses a LiteLLM proxy to collect LLM traffic. Validates the gateway tier and the idea of pushing updated “resources” into an unmodified agent.
MCP 2026-07-28 made the core stateless and moved Tasks into an extension: a call can return a task handle that clients poll (tasks/get), update or cancel. tasks/list was removed. Experiments become handles with get, update and cancel. We also expose PromptLab as an MCP server.
A2A reached v1.0 in 2026 under the Linux Foundation’s Agentic AI Foundation: Agent Cards, tasks with states such as input-required and rejected, signed cards. Optional binding so an agent-style workflow can be driven as an A2A agent; our run states align with its lifecycle.
OpenAPI 3.2 (Sept 2025) adds first-class streaming media types (SSE, JSONL) through itemSchema and the QUERY method, still on JSON Schema 2020-12. Contract-first in 3.2, run events streamed as SSE, QUERY for complex searches.
LLM judges show position, length and self-preference bias, and the size of each bias varies by judge. Practice: a human gold set, calibration (for example Cohen’s kappa), order swapping, cross-family ensembles. An ICML 2026 paper shows how to correct judge-induced bias in reported scores. Judges are versioned, calibrated artifacts. Reports use bias-corrected intervals when calibration data exists.
For prompt comparisons, practitioners converge on paired designs, bootstrap intervals on per-item differences, McNemar for pass/fail, an untouched confirmation set and multiple-comparison correction. Anytime-valid intervals allow safe peeking. A stats engine is a core service, not a chart added later.
Agent-eval practice: record tool and retrieval outputs once and replay them. Replay should never silently fall through to live calls. Tapes, and a strict REPLAY mode where a miss fails the trial.
Durable-execution engines (Temporal, Restate, DBOS on Postgres) are now standard under long-running agent workloads. Experiments run as durable workflows.
Langfuse v4 runs on Postgres, ClickHouse, Redis and S3-compatible storage. ClickHouse acquired Langfuse in January 2026. We use the same storage shape.

Source quality: specifications and official docs wherever possible. Several 2026 details come from vendor and practitioner blogs, so re-verify before pinning versions.

Second pass: what the frameworks already expose.

  • Google ADK lets one Plugin, registered on the Runner, hook every agent, tool and model call, and ships an adk api_server with sessions, /run and /run_sse.
  • LangChain v1 agents accept middleware (dynamic_prompt, wrap_model_call) that receives the model request and can rewrite it.
  • LangGraph checkpoints support replay and fork (change state at a past checkpoint, then resume). Its Agent Server exposes threads, runs, per-run configurable and context, graph introspection, and A2A and MCP endpoints.
  • OpenInference ships instrumentors for LangChain and LangGraph, Google ADK, CrewAI, LlamaIndex, OpenAI Agents, DSPy and more, so observation needs no new tracers.
  • Consequence: integrate through each framework’s own hooks and servers instead of asking teams to rewrite code around our SDK. Section 5 builds on this.

Third pass: standards and techniques this revision rests on.

  • OpenInference already instruments the model SDKs themselves (OpenAI, Anthropic, Google GenAI, Bedrock, LiteLLM, Mistral, Groq, VertexAI), which shows that a stable interception point exists at the model-client boundary in each of them.
  • OpenFeature’s Remote Evaluation Protocol (OFREP, spec version 0.3.0) standardizes flag evaluation with a per-request evaluation context, bulk evaluation with ETags, and community providers in many languages.
  • Record-and-replay eval tools key cached model, API and judge calls by the canonical request, and their strict replay mode turns a miss into a failure instead of a live call.
  • τ-bench and its successors evaluate agents against an LLM-simulated user with a hidden goal and check the final database state, and they report pass^k because one success can be luck. A 2026 study found that changing only the user simulator changes measured agent performance.
  • Metamorphic testing checks expected relations between outputs of semantically equivalent inputs, which needs no labels. A 2026 study found that model scale did not predict robustness under such transformations.
  • A2A v1.0 defines its data model in Protocol Buffers and publishes JSON Schema generated from it.

3. Design principles#

  1. Intercept at universal boundaries before framework-specific ones. Model calls and data reads are where every framework meets reality.
  2. The workflow stays where its data is. Database access, credentials and network position remain on the customer side.
  3. Every call is a function of its content-addressed request. Whatever is non-deterministic is masked or keyed explicitly, which makes caching, replay and fork correct.
  4. Prompts are configuration, resolved at call time with an evaluation context. Changing a prompt is never a deploy.
  5. Everything is a trace, and every trace is replayable.
  6. One contract for any granularity. A single call, a step, a subset or the whole workflow all use the same run request.
  7. Determinism is visible. Every result states its mode, cache hits and misses, and replay fidelity.
  8. Production never depends on PromptLab. Interceptors and resolvers fail open to cached or built-in prompts.
  9. Failures count. A crashed trial is a scored failure.
  10. Security starts in the data plane. Sensitive payloads can stay with the customer.
  11. Simple to operate. One deployable control plane first; split services only when measured load demands it.

4. System architecture#

The system splits into a control plane that decides what to run and judges results, and a data plane inside the customer’s runtime where the workflow runs against real data. Three interception planes inside the data plane are what make any framework testable.

Why a modular monolith. The control-plane modules share one transactional model (registry, experiments, promotions) and modest traffic. One deployable with strict module boundaries ships faster and fails in fewer ways than a dozen services. The three hot paths scale with trace and trial volume, so they run separately from day one. Larger tenants move into their own cell, a full copy of the stack, which also serves data residency.

Lifecycle of one experiment

  1. A user, CI job or agent posts an experiment: workflow, variants (overlays), dataset version, evaluators, mode, budget.
  2. The orchestrator expands it into trials (variant × item × repetition), interleaved so provider drift hits every variant alike.
  3. Each trial reaches a runner through its invocation profile. The run carries the overlay reference, mode, cache scope, sample index, trace context and an idempotency key.
  4. Inside the workflow, the model plane resolves and applies the overlay to each matching model request and looks it up in the memo cache. The I/O plane serves or records data reads. Both emit spans.
  5. Results return with cache hits, misses and the hash of the overlay actually applied.
  6. Evaluators score outputs and spans. The statistics module compares variants item by item.
  7. The result is a reproducible record. A promotion gate may move an alias, and an optimizer may reuse the same machinery as its evaluate().

5. Integration: three interception planes and a narrow waist#

Any workflow becomes testable by intercepting it at three planes. Two of them, the model plane and the I/O plane, are framework-independent, so a new framework works on day one. The third adds framework-specific names and templates, and it mostly comes from existing open-source instrumentors.

5.1 The three planes#

Plane What it sees What it enables Mechanism Framework-specific code
Model plane The canonical model request: system prompt, messages, tool definitions, parameters, and the response Steer prompts, tool descriptions and parameters; memoize; cost and latency An in-process interceptor on each model SDK (OpenAI, Anthropic, Google GenAI, Bedrock, LiteLLM and others), loaded without code changes the way OpenTelemetry’s zero-code agents are; or the provider gateway by base URL None
I/O plane Requests and responses of HTTP, SQL, vector-store and MCP clients Capture and replay the data the flow read; block writes during tests OpenTelemetry auto-instrumentation libraries, extended with payload capture in experiment runs None
Semantic plane Agent, node, tool and step names; templates and variables; graph structure Call-site identity, per-step scoring, template-level edits, native checkpoints OpenInference instrumentors; an optional thin shim (ADK plugin, LangChain middleware); pl.prompt for hand-rolled code Small and optional

Call-site identity without framework code. When the model interceptor fires, it reads the active span ancestry the framework instrumentor has already created, for example an invoke_agent billing span with a chat span inside it. From that it derives a stable call_site_id such as agent:billing/llm. With no instrumentor present, it falls back to a fingerprint of the request’s static parts.

Invocation is the fourth concern and the only one outside the workflow process: an invocation profile drives a surface the workflow already exposes (LangGraph Agent Server, adk api_server, A2A, MCP, plain HTTP, a CLI, or an in-process call). See 7.5.

5.2 Overrides are structural patches on the canonical request#

An overlay entry targets paths inside the canonical request for one call site, written as JSON Patch operations (RFC 6902). The same override then means the same thing in every framework.

json
{
  "call_site": "agent:billing/llm",
  "patch": [
    {"op": "replace", "path": "/system", "value": {"template_ref": "prompt://billing.system@v14"}},
    {"op": "replace", "path": "/tools/refund_lookup/description", "value": "Look up refund status by order id. Never guess an id."},
    {"op": "replace", "path": "/params/temperature", "value": 0}
  ]
}

Templates with variables. Static instructions, tool descriptions and parameters can be replaced outright. When a prompt embeds per-run values (a user name, retrieved text, a date), replacing the whole string would erase them. Two mechanisms handle that: the semantic plane supplies the template and its variables where a shim or pl.prompt exists, and template induction (5.7) infers the holes elsewhere. Steer verification (7.3) still confirms that each override actually landed.

5.5 Canonical Workflow Model#

The narrow waist is a framework-neutral graph of what a workflow does: model calls, tool calls, retrievals, agents, routers and handoffs, subgraphs and human steps. Each node has a call_site_id, edges to its parents, and its tunables. It is built from traces and enriched by static introspection where available (the LangGraph graph endpoint, an ADK agent tree, an A2A agent card). Trace views, per-step scoring, optimizer component selection and statistics read only this model, so N frameworks and M platform features cost N + M integrations, not N × M. In multi-agent systems a handoff is an edge, each agent’s instruction and handoff description are tunables, and evaluators score each agent and the trajectory separately.

5.6 Tunables, not just prompts#

A tunable is a typed parameter on a call site: system instruction, template with variables, tool name and description, few-shot examples, model and sampling parameters, retrieval parameters (k, thresholds, reranker), routing or handoff text, guardrail text. Each type has a contract (required variables, schema, maximum length). Text tunables are GEPA components; numeric and enum tunables go to grid, Bayesian or bandit search. One overlay can mix them, so a multi-agent system is tuned as one system.

5.7 Template induction#

Comparing several captured renderings of the same call site reveals the static skeleton and the variable holes. An override can then edit the skeleton while the holes are refilled on each call. It is best effort, reports a confidence score, and refuses when it cannot locate the holes. The same technique suggests pl.prompt placements for teams that want exact templates.

5.8 Low-friction onboarding#

  1. Zero code: promptlab run -- python app.py (or the equivalent Node launcher) loads the interceptors and auto-instrumentation, the same pattern as OpenTelemetry zero-code agents. For other stacks, point the model client’s base URL at the gateway.
  2. Configuration: promptlab init detects the framework and writes a promptlab.yaml with the invocation profile, effect policy and prompt source.
  3. Verification: promptlab doctor probes each capability: a span arrives, a canary phrase swapped into a prompt appears in the model request, a repeated call hits the cache, a captured read replays. A failed probe lowers the declared capabilities instead of failing the integration.
yaml

6. Memoized execution: replay and fork without checkpoints#

Every model call and every captured data read is keyed by a hash of its canonical request. Re-running a workflow with an overlay reuses every call whose request is unchanged and runs live from the first call that differs. That single mechanism provides replay, fork-from-step, cheap re-runs and variance reduction in any framework.

6.1 How it works#

  1. Canonicalize each request into a provider-neutral form: sorted keys, normalized whitespace, and configured volatile fields (timestamps, request ids) masked.
  2. Key it: hash of the canonical request, pinned model version, sample index, and for data reads the capture epoch.
  3. Look up on every call. A hit returns the recorded response and emits a span marked as a hit. A miss executes according to the mode and records the result.
  4. Changes propagate by themselves. Downstream requests embed upstream outputs, so a changed prompt changes its own request and, transitively, every request that depends on it. Unchanged upstream calls still hit. Fork-from-step is derived, not declared.
text
Baseline run (recorded)            Variant run: the summarize prompt changed
kb_search(q)       vector read     kb_search(q)       HIT   same request
plan               model call      plan               HIT   same request
summarize          model call      summarize          MISS  request changed → live
classify           model call      classify           MISS  input changed → live
update_ticket      HTTP write      update_ticket      BLOCKED  write effect, mocked

Why this beats checkpoints. It needs no framework support, so it works the same in ADK, LangGraph and plain Python. It works inside agent loops, because calls hit until the trajectory diverges and run live after that. The cache is shared across experiments, so a hundred candidate prompts pay for the upstream calls once. A tape is simply a named, frozen set of memo entries, for example the set committed for CI.

6.2 Modes are cache policies#

Mode Model calls Data reads Typical use
LIVE Always executed, recorded Always executed, recorded Ground truth; the numbers you ship on
FORK (default while iterating) Hit if unchanged, otherwise live Hit if unchanged, otherwise live read (or fail, by policy) One prompt or several, inside the real flow
REPLAY From cache; a miss fails the trial From cache; a miss fails the trial Deterministic CI regression
HYBRID Per call-site policy Per boundary policy Some data volatile, some stable

Every result reports its mode, hits, misses and replay fidelity (the share of calls served as recorded). A REPLAY number is never mistaken for a LIVE one. Working rule: iterate in FORK, gate in REPLAY, confirm in LIVE.

6.3 Common random numbers#

The sample index is part of the key, so repetition r of variant A and repetition r of variant B receive identical upstream samples, including identical retrievals. Their paired difference then reflects the prompt change rather than upstream randomness, the classic variance-reduction technique of simulation studies, and fewer items are needed for the same confidence. Two cautions: results are conditional on the shared upstream samples, so enough repetitions and items are still required; and the cache never fabricates new samples, because a new sample index is always a miss.

6.4 Correctness guards#

  • Volatile masks keep timestamps and random ids from causing false misses, and promptlab doctor flags unstable fields it detects.
  • Model version is keyed; code version is recorded but not keyed. An identical request to the same model is a draw from the same distribution, whoever built it.
  • Capture epoch makes stale data visible. Each result shows how old its captured reads are, and scheduled LIVE runs detect drift.
  • Fidelity checks: a sampled fraction of hits is re-executed live and compared, which catches caching bugs before they mislead anyone.
  • Isolation: the cache is per tenant and write-once, and its entries live in the data plane when payloads are sensitive.

6.5 Effect safety#

The I/O plane classifies calls as read or write by default (HTTP GET versus POST, PUT, PATCH and DELETE; SQL SELECT versus statements that modify data; MCP tools by annotation), and configuration or decorators override the default. Outside LIVE mode, writes are never executed: they are mocked from the recording or blocked. LIVE runs deny writes unless an experiment explicitly allows them against a sandbox target.

Your case: workflows write to production PostgreSQL. Protection is layered, strongest first:

  1. Never test against the production primary. Test runs call a separate test deployment of each service, connected to a staging copy or a read replica.
  2. Enforce it in Postgres. The test deployment connects with a role that has SELECT-only grants and default_transaction_read_only = on, so any write fails inside the database whatever the code does.
  3. Block and score writes in the I/O plane. In FORK and REPLAY modes, write statements become recorded no-ops, so the workflow keeps running and the attempted write becomes a test signal (for example, did it try to refund the right order).
  4. Disposable databases for write tests. A LIVE test that must exercise writes runs against a per-run database or schema restored from a snapshot, never a shared one.

Rolling back a transaction around the run is not relied on: services open their own connections and commit, and a rollback cannot undo effects outside the database.

6.8 Standalone prompt testing and model upgrades (Phase 2)#

The first release tests a prompt as a function: template, variables, model and parameters in; output out, scored and compared statistically. No workflow runs and no service or production database is touched, so it delivers value on day one. Everything it builds (registry, datasets, evaluators, statistics, experiments) is reused unchanged when in-workflow testing arrives.

Its weakness is input realism, and the roadmap fixes it. A prompt tested on invented variables can pass and still fail on what the workflow really sends it. Inputs therefore come from three sources, in rising realism:

  1. Hand-written items, or CSV and JSON uploads.
  2. Values copied from application logs.
  3. Inputs captured from real ADK and LangGraph calls once the SDK is in place (Phase 1): the exact rendered variables, including what was read from Postgres. A standalone test on captured inputs is a faithful single-call test of the real workflow.

The prompt unit. A prompt version bundles the messages, typed variables, an optional output schema, and the model with its parameters, so a model change is a new prompt version that can be compared and promoted like any other. Templates use ADK’s {variable} syntax so existing ADK instructions import unchanged.

Rules for every contract

  • Extensions carry reverse-DNS ids and versions. A peer ignores unknown extensions unless they are marked required.
  • Every POST that creates work takes an Idempotency-Key. Lists use cursors. Prompt and overlay fetches use ETags.
  • Errors use RFC 9457 problem details. Content hashes are SHA-256 over RFC 8785 canonical JSON, so equal content has an equal hash in every language.
  • Every request carries W3C traceparent and baggage, so runs, spans and scores join up.

7.6 Optimizer adapter, MCP facade and A2A binding#

GEPA adapter. A GEPA candidate (a dictionary of component name to text) is the overlay’s text entries. evaluate(batch, candidate, capture_traces) becomes a batch of runs through the Run Protocol with that overlay, returning outputs, scores and, on request, trajectories built from traces. make_reflective_dataset slices the traces per component by call_site_id and adds evaluator feedback text. MCP facade. PromptLab is also an MCP server. A2A binding. A workflow’s agent card is generated from its manifest, and run states map one-to-one to task states.

7.7 Services with their own API contracts#

Each workflow keeps its own API, and PromptLab adapts to it through a declarative endpoint adapter. No developer has to change a contract or a coding style to be testable.

What an adapter declares

  • The test deployment’s base URL and a reference to its credentials in the vault.
  • A request mapping from dataset item fields to the service’s own request body, path and headers.
  • A response mapping that extracts the output and any extra fields to score.
  • Optional multi-step handling (create a session, then post a message) and asynchronous patterns (poll a job id until done).
yaml
# workflows/refund-assistant.yaml
workflow: refund-assistant
framework: adk
invoke:
  profile: http-generic
  base_url: https://refund-assistant.test.internal      # test deployment, read-only database role
  auth: {secret_ref: vault://promptlab/refund-assistant}
  request:
    method: POST
    path: /api/v2/refunds/assist
    body:
      customerId: "{{ item.input.customer_id }}"
      text: "{{ item.input.message }}"
      channel: web
  response:
    output: "$.result.reply"
    fields: {decision: "$.result.decision", order_id: "$.result.orderId"}
  async:                                                  # only if the API is asynchronous
    poll: {path: "/api/v2/jobs/{{ response.jobId }}", until: "$.status == 'done'", every_ms: 500}
openapi: https://refund-assistant.test.internal/openapi.json   # optional: draft the mapping from it

How overlays reach the code. PromptLab adds W3C traceparent and baggage headers (run id, overlay reference, mode) to each call. Inside the service, the interceptor loaded by the launcher at the container entrypoint reads that context from the incoming request and applies the overlay to the model calls made while serving it. This works when the service’s web framework is instrumented to extract incoming context (OpenTelemetry auto-instrumentation covers FastAPI, Flask and Django). Work handed to background tasks or queues must carry the context along, and promptlab doctor checks that a canary overlay survives the whole request path.

Onboarding helpers

  • promptlab adapter draft proposes the mapping from the service’s OpenAPI document (FastAPI generates one automatically).
  • promptlab adapter test sends one dataset item and shows the mapped request, the raw response and the extracted output.
  • Datasets can be seeded from sampled real requests to the service, so items already arrive in the service’s own shape.

Contract drift. The adapter is versioned with the workflow version, and a run fails fast with a clear error when a response path stops matching, instead of scoring empty outputs.

9. Experiment engine#

An experiment is a durable workflow, so a crash, deploy or provider outage never loses progress or double-counts a trial.

  • Orchestration. One durable workflow per experiment (Temporal by default; DBOS on Postgres or Restate are viable at smaller scale), one child workflow per trial, signals for cancel and pause, queries for live progress.
  • Scheduling. Trials are variant × item × repetition, interleaved so provider drift and time-of-day load hit every variant alike. Seeds are fixed and model versions pinned. Repetitions exist for stochastic workflows and feed a hierarchical bootstrap (Section 12).
  • Concurrency. Adaptive (AIMD) per runner within the runner’s declared limit, a per-tenant token bucket, and provider rate limits shared through the provider gateway.
  • Idempotency. Each trial has a deterministic key (experiment, variant, item, repetition), so retries cannot double count.
  • Budgets. Tokens, dollars and wall-clock. Soft warning at 80 percent, hard stop at 100. Partial results stay valid because the paired analysis uses only items finished by every variant, and coverage is reported.

Experiment types: A/B, multi-variant, factorial (tunables × model), leave-one-out ablation, and online canary or shadow comparison on sampled production traffic. Testing granularity (one prompt, a subset, everything) follows the matrix in 6.7.

What a test case can be. Static input and output pairs cannot test an agent that asks follow-up questions or changes state, so the dataset model supports five kinds.

Kind Contents Scored by
Static item Input, optional expected output Output and trace evaluators
Captured run A production or staging trace with its captured reads Comparison against the original output, plus guard metrics
Conversation Prior turns and the next user message Turn-level evaluators
Scenario A simulated user with a persona and hidden goal, an initial environment state, a success check on the final state State check plus judge, reported as pass^k over k trials
Metamorphic group An item, semantics-preserving transformations (paraphrase, reordering, added context) and the expected relation between outputs Relation violations; no labels needed

Simulated users are versioned and calibrated like judges, because the choice of simulator changes measured agent performance. A persona library (cooperative, terse, impatient, withholding) keeps tests from flattering the agent.

Production traces as datasets. Captured production runs are sampled and stratified by slice (intent, customer tier, language), then re-executed in FORK mode. The changed call runs on exactly the context production saw, with no curation step. Results are scored against the original output with pairwise judges and guard metrics, and human feedback that arrives later attaches as labels. Captures stay in the data plane under the tenant’s retention rules.

10. Evaluation service#

Evaluators score outputs and also individual steps, because in a multi-prompt workflow a wrong final answer says little about which prompt failed.

Evaluator kind Examples Runs where
Deterministic JSON schema validity, regex, exact match, retrieval precision and recall, tool-call trajectory rules, budget limits Workers, or inside the customer plane
LLM judge Rubric score, pairwise with order swap, reference-based faithfulness using the retrieved context from the trace Workers via the provider gateway
Human Annotation queues, gold-set labeling UI
Composite Weighted or constrained combinations of quality, cost, latency and safety Stats engine

Evaluator contract. POST /v1/evaluate receives the item, the output, the expected value, a trace reference and optional context. It returns scores, each with a name, value or label, an explanation, an optional span_id and the evaluator version. The shape deliberately matches the OpenTelemetry gen_ai.evaluation.result event, so scores can also be emitted into any OTel pipeline. Custom evaluators in any language implement this endpoint, or run in-process through the SDK.

Judge governance

  • A judge is a versioned artifact: model, prompt, parameters, and its calibration record.
  • Calibrate against a human gold set before trusting a judge, and report agreement (for example Cohen’s kappa) beside every judge-scored result.
  • Mitigate known biases by default: order swap in pairwise comparison, length-controlled rubrics, and cross-family ensembles so a judge never grades its own family alone.
  • When calibration data exists, report bias-corrected estimates and intervals, following the ICML 2026 method for correct reporting of judge-based scores.
  • Judge prompts can themselves be optimized, but only against human labels, never against their own scores.
  • Judge cost has its own budget line, tracked as a share of total experiment cost.

Trace-aware scoring. Evaluators can read spans: retrieved chunks, tool calls, handoffs. Step scores attach to the span id and call site, which feeds credit assignment in Section 11.

11. Optimization service#

Optimizers are jobs that call one adapter (7.6) and never see the framework.

Algorithm Use it when
Manual with side-by-side diff A person is iterating in the UI
Few-shot bootstrap The tunable is an example set
Instruction search (MIPRO-style) One or few prompts, a clean scalar metric
Reflective evolution (GEPA), default Several text tunables, rich textual feedback, a small rollout budget, multiple objectives (Pareto)
Grid, Bayesian or bandit search Numeric and enum tunables, or online allocation

GEPA is the default because it learns from full traces and written feedback, keeps a Pareto set of candidates, and is already integrated by DSPy and MLflow, which is a sign of convergence. It also benefits from a strong reflection model, so the reflection model is a per-tenant setting.

Spend the budget where it matters. Candidates are first scored on a small subset, and only survivors advance to the full validation set (successive halving). Because the memo cache is shared, every candidate reuses the same upstream calls, so a generation of candidates costs little more than the calls they actually change.

Data discipline (enforced by the platform, not by convention)

  • Users never manage splits: PromptLab is a user testing platform, and experiments run on every row the user chose. Inside an optimization job only, the optimizer holds part of the rows out automatically, reflecting on some and selecting on others, then confirms the winner on rows it never saw.
  • A candidate that wins during selection but loses on the held-out rows is recorded as overfit, and counts against that optimization run.

Guardrails

  • Static checks before any run: required variables present, schema constraints kept, maximum length, no secrets or forbidden patterns.
  • Length and cost are objectives, which counters prompt bloat from repeated mutation.
  • A safety and regression suite is a hard constraint, never a tradeable objective.
  • Traces fed to a reflection model are redacted first, and datasets, traces and retrieved text are treated as untrusted data inside reflection and judge prompts (delimited, no tool access).

Multi-agent credit assignment. The workflow model gives each agent and call site its own slice of every trace. Reflection and component selection work per tunable. A leave-one-out ablation then confirms that a proposed change actually carries the gain, rather than trusting the optimizer’s story.

Output. Each candidate becomes an immutable prompt version with lineage (parent, algorithm, experiment ids) and the label proposed. Nothing reaches an environment without passing the promotion gate in Section 12.

12. Statistics and promotion gates#

A prompt change ships only when a paired comparison, a held-out confirmation and the guard metrics all agree.

12.1 The statistics engine#

Question Method
Is variant B better than A on the same items? Paired bootstrap interval on per-item differences, with a permutation test as a cross-check
Pass or fail metric McNemar on discordant pairs (exact test for small counts)
Repetitions, or clustered items such as conversations Hierarchical bootstrap: resample cases (or whole clusters), then repetitions
Several variants or metrics Holm or Benjamini–Hochberg correction, with the primary comparison declared before the run
Can this dataset detect the effect that matters? Power and minimum-detectable-effect planner computed from observed variance, shown before the run
Can I stop early? Anytime-valid confidence sequences, so peeking does not inflate error
Judge-scored metric Bias-corrected estimate when calibration data exists
Is the winner real, or a fluke of selection? Inside optimization only, confirmation on rows the optimizer never saw; for human edits, the comparison runs on the full chosen dataset

One practitioner source suggests that fewer than about 100 paired examples is below the resolution of a credible prompt A/B. Treat that as a rule of thumb: the planner computes the real answer from your data’s variance. Your datasets are typically 10 to 20 rows, so in Phase 2 the row-by-row comparison, people’s ratings and repetitions are the primary evidence, and a statistical verdict appears only from 30 rows (Requirements tab, ST-006).

Variance reduction comes from the engine. Common random numbers (6.3) give both variants identical upstream samples, which tightens paired intervals at no extra cost. The power planner accounts for this, so the item count it recommends reflects the real design.

Guard metrics use non-inferiority tests: cost, latency, schema validity and the safety suite must not get worse by more than a stated margin, however much quality improves.

12.2 Promotion#

Environments are aliases on prompt versions: proposed, candidate, staging, canary, prod.

  1. proposed: created by a person or an optimizer and passed the static checks.
  2. candidate: beats the baseline on the chosen dataset with an interval above zero, and the guard metrics pass.
  3. staging: passes the safety suite and a LIVE confirmation run.
  4. canary: shadow traffic first, then a small share (1 to 5 percent), with online evaluators on a sampled fraction.
  5. prod: ramps up, with automatic rollback when online scores or guard metrics degrade.

Protected aliases need an approver (Langfuse offers protected prompt labels in the same spirit). Every move writes a Promotion record that links to its evidence.

12.3 CI/CD#

  • promptlab ci runs on a pull request: a REPLAY regression against the committed tape set, a report with deltas and intervals, and a failing status on any guard violation.
  • A scheduled LIVE run against fresh data catches tape staleness before it misleads anyone.
  • In Git-native mode the optimizer opens the pull request itself, and the same gate decides whether it can merge.

13. Observability and data layer#

Ingest. OTLP over gRPC or HTTP through an OpenTelemetry Collector. A normalizer accepts both OpenInference (llm.*) and OpenTelemetry GenAI (gen_ai.*) attributes, and stores the convention version with every batch. Our own attributes live under promptlab.*: workflow id and version, call site id, tunable id and version, overlay hash, experiment and trial ids, mode, tape hit.

Content capture. OpenTelemetry leaves prompt and completion content off by default. We turn it on for experiment runs only. A redaction processor runs in the customer plane before export, and large payloads go to object storage with a reference in the span.

15. Scalability and reliability#

  • Stateless scale-out. API, runner gateway, evaluator and optimizer workers scale horizontally. State lives in the four stores and in the durable orchestrator.
  • Sizing formula. Spans per second = concurrent trials × spans per trial ÷ average trial seconds. Example only: 2,000 concurrent trials × 30 spans ÷ 20 s = 3,000 spans per second. Replace the inputs with your real numbers (open question 3).
  • Backpressure. Runner leases, adaptive concurrency, per-tenant token buckets, circuit breakers on providers, and priority queues so CI runs are never starved by bulk optimization.
  • Caching. An LLM response cache keyed by the canonical request for judge and reflection calls (record once, replay), and an SDK-side cache of prompts and overlays with ETag and stale-while-revalidate.
  • Reliability targets (proposal). Control API availability 99.9 percent; trial dispatch p95 under 5 seconds; experiments survive a control-plane restart because they are durable; no span loss because ingest is queued and replayable.
  • Disaster recovery. Postgres point-in-time recovery, ClickHouse replicas, object-store versioning. RPO and RTO to be set with you.
  • Regions. One control plane per region with data pinned by tenant, which is also how residency requirements are met.

Risks this revision introduces, and their mitigations

  • Interceptor drift. Model SDKs change often. Mitigate with a conformance suite per SDK version, a published support matrix, and the gateway as a fallback.
  • False cache hits. A missed volatile field or an unpinned model alias could return a stale answer. Mitigate with keyed model versions, doctor detection of unstable fields, and sampled live re-execution of hits (6.4).
  • Payload capture is sensitive. Recording reads means storing customer data. Mitigate by capturing in experiment runs only, keeping captures in the data plane, encrypting per tenant and applying short retention.
  • Standards still settling. OFREP is at 0.3.0 and the OpenTelemetry GenAI conventions are in Development status, so both sit behind adapter layers.

Decisions recorded, and what is still open

  1. Frameworks: ADK and LangGraph first, through one SDK with framework adapters; LangChain, DeepAgents and others follow (updated 24 October 2026).
  2. Data and traces: data in PostgreSQL; no tracing today, so PromptLab provides it.
  3. Scale: thousands of workflows; start on Postgres and measure against the fleet targets, with thresholds in Section 13.
  4. Starting point: prompt testing inside connected workflows first (Phase 1), then experimentation on database datasets (Phase 2), then sign-in, approvals and advanced features (Phase 3). Build on your own Postgres.
  5. Production writes: yes, so test runs use read-only test deployments enforced in Postgres (6.5).
  6. Approvals: leads approve promotions; no compliance regime assumed.

Still open

  • Which candidate model is the first upgrade, and which prompts matter most?
  • Is a staging copy or a read replica of the production database available for test deployments?
  • Do any services hand work to background jobs or queues? This affects context propagation (7.7).
  • How many workflows and prompts will the first teams bring? This sizes Phase 1 and the Phase 2 capacity targets.

2.4 What “exactly as the workflow executes” means#

PromptLab never rebuilds a model call, a retrieval, a memory lookup or a tool on its side. It runs the workflow’s own code inside a workflow instance and proves the result matches production with a parity check (EXEC-006).

Aspect Must match How it is guaranteed
Rendering Template, variable values, escaping, message order, placement of system text and examples Rendered by the workflow’s own template object or pl.prompt
Model call Model and version, parameters, tool definitions, structured-output schema, safety settings, credentials The call goes through the call site’s own bound model object and client
Client behavior Retries, fallbacks, timeouts, callbacks, rate limits The same client instance and configuration
Post-processing Output parser, validation, repair steps, code after the call Node and workflow scopes run that code; prompt scope runs the parser
Context, retrieval, memory, tools Upstream state, retrieved rows, memory reads, tool results, date and time The workflow’s own code runs; outside dependencies are called live read-only, or served from what was recorded, at the client-library level (section 5.6)
Concurrency Fan-out width, max_concurrency, branch isolation The workflow’s own runtime

4.3 Who connects to whom#

  • Jobs. The SDK inside each workflow process opens one outbound connection to PromptLab and keeps it open. PromptLab sends work down it: run a prompt, run a node, run the workflow, run a doctor check, cancel. The workflow needs no inbound port for PromptLab.
  • Prompt resolution. Instances fetch the active prompt versions for their environment over HTTPS and cache them in memory and on disk.
  • Traces. Traces and recorded inputs are exported asynchronously to PromptLab.
  • TLS everywhere, including localhost. promptlab dev certs creates a local certificate authority; the SDK trusts it through PROMPTLAB_CA_BUNDLE. Certificate checks are never turned off.

4.4 How a prompt resolves at run time#

On every call, in this order:

  1. The edit being tested, when the call belongs to a PromptLab test run (test environments only).
  2. The release pinned for this workflow run: the set of active versions for the instance’s environment, fixed when the run starts (REL-004).
  3. The last release cached on disk, when PromptLab is unreachable at start.
  4. The default in code.

6. Phase 2: experimentation on small datasets#

Goal. Test prompt changes on small datasets, typically 10 to 20 rows, read from the read replica or entered by hand, with the workflow’s expected input and output identified automatically. Users compare every row old beside new, rate outputs, run each row several times to see how stable the output is, and read a summary.

Why small datasets change the design. With 10 to 20 rows, a statistical test can detect only very large differences, so most comparisons would come back inconclusive. PromptLab therefore makes the row-by-row view and people’s ratings the main evidence, counts rows that got better, worse or stayed the same, runs each row several times so variation is visible, and shows a statistical verdict only when there are enough rows to support one.

No train, validation or test split. PromptLab is a user testing platform: every experiment runs on the rows the user chose, all of them, and reports on all of them. Users pick the rows they want.

Exit gate. On the reference workflow, PromptLab identifies the input and output formats, builds a 20-row dataset from a read-replica query and another from pasted comma-separated values, runs current and edited prompts over every row three times each, and shows row-by-row results, ratings and a summary for the branch and the final output (section 11.2).

9. UI/UX requirements#

9.1 Principles#

  1. Show the prompt where it lives. Every prompt is reached from its place in the workflow.
  2. Compare first. Old and new appear side by side with differences highlighted.
  3. Never hide how a result was made. Scope, release, instance and (from Phase 2) dataset, judge and row count sit next to every result.
  4. Plain language for business users, full detail one click away for developers.
  5. Evidence over averages (Phase 2): verdicts come from intervals.
  6. Safe by default. Production changes show what will change and need confirmation.

9.2 Journeys#

Phase 1, business user. Open a workflow and see its map; open a prompt and read what feeds it and what reads its output; change the wording; pick a recent real run and run the prompt on it; see old and new output side by side, for the step and the final output; save; make it active.

Phase 2, business user. Open a prompt; see the workflow’s expected input and output; pick 10 to 20 rows from the read replica, or type an input, or paste comma-separated values; run current against edited over every row, three times each; go through the rows old beside new and rate them; read the counts; activate the change.

Phase 3. Sign in; request activation; a lead approves; get notified.

PromptLab UI/UX design

The product design for PromptLab: the principles behind it, the design system, the components, ten high-fidelity screens, the states and errors, accessibility, responsive behavior, content rules, and the frontend and quality plan. It turns the UX requirements in the Requirements tab (UX-001 to UX-022 and UX-101 to UX-107) into something a designer can refine and an engineer can build. All screens show sample data from the refund-assistant example. Model names and numbers are illustrative. The screens for the newer requirements UX-023 to UX-031 (workflow map, business prompt editor, run result, change sets, code-changed review, workflow list, input and output formats) are specified in the Requirements tab and not yet drawn here; phases follow the Requirements tab’s three-phase plan.

1. Design intent#

PromptLab exists to answer one question quickly and honestly: is this prompt or model change better, on what, and how sure are we? Everything in the interface serves that question. A person edits a prompt, tries it, tests it on real cases, reads a verdict with its evidence, and asks a lead to approve it. The design makes each step obvious and makes the evidence impossible to misread.

1.1 Visual direction: ink for actions, color for evidence#

Most tools use color to decorate. PromptLab spends it only where it carries meaning.

  • Chrome and actions are monochrome. Navigation, buttons, tabs and selection use ink on paper. The primary button is ink, not a brand color.
  • Color appears only in evidence: verdicts (better, worse, guardrail), chart series (baseline and up to three variants), and the focus ring. A reader who sees green or red knows it is a result, never a button.
  • Run mode is shown by shape and texture, not hue: live is solid, replay is hatched, fork has a heavy left edge. A replayed result can never be mistaken for a live one, even in grayscale.
  • The signature element is the interval: a point with a line through it, drawn against a zero line. It appears in the results chart, in table rows and in the logo. The product's job is to show uncertainty, so uncertainty is its mark.
  • Type is IBM Plex Sans with tabular figures for every number, and Plex Mono only for prompts and code. Its precise, engineered letterforms suit a tool built on measurement.

1.3 What we deliberately leave out#

  • No single score or leaderboard. A ranked list of variants invites picking a winner from noise.
  • No auto-promote. The product never moves a production alias without a person with the lead role approving it.
  • No hidden defaults on statistics. Confidence level, correction method and equivalence band are visible and changeable by editors, locked for approvals.
  • No color-only status. Every state has an icon and a word.
  • No modal-first workflows. Dialogs are for protected actions and confirmations only; creation and editing happen on pages with URLs.

Rules for using color:

  • Verdict colors appear only on a verdict pill, a verdict word or a chart mark, and always beside an icon and a word.
  • Series colors are assigned in a fixed order (baseline, A, B, C) and paired with a marker shape: circle, square, diamond. Four series is the maximum on one chart.
  • Selection is ink, not blue: a heavy left edge on rows and an underline on tabs. Blue appears only as a link, a focus ring, an information alert, or variant A.
  • Tints (better, worse, warn, info backgrounds) are for pills and alerts. Never use a tint as a page or panel background.

4.2 Typography#

  • Families: IBM Plex Sans for the interface, IBM Plex Mono for prompt text, code and ids. Fallback: the system UI font. The fonts ship with the app (self-hosted, Latin subset, 3 weights of Sans and 1 of Mono) to avoid a network request and a flash of unstyled text.
  • Numbers: tabular figures everywhere (font-variant-numeric: tabular-nums) so columns of figures align and deltas can be compared by eye.
  • Density: the default 13 px body suits a data-heavy tool. A comfortable mode (15 px body, taller rows) is available in settings and is the default for approvals and review on phones.
  • Line length: prose in help text and rationales stays under 70 characters per line.
  • Weight over size: hierarchy comes from weight and position first. Only the page title, the verdict line and section headings change size.

4.3 Space, shape and elevation#

The interface separates regions with 1 px rules and spacing instead of stacked cards. Panels exist only where content needs a boundary (forms, inspectors, tables). Shadows appear on floating layers only: popovers and dialogs.

4.5 Iconography#

Icons are outline-only, 16 px in controls and 20 px in empty states, with a 1.75 px stroke. They never stand alone for meaning: each has a visible label or an accessible name. The set is the open-source Lucide library, which is ISC licensed.

4.6 Data visualization#

The main chart is the interval plot: one row per variant and metric, a point for the estimated change, a line for the 95 percent interval, a zero line, and a shaded band for changes too small to matter.

  • Filled or hollow: a filled marker means the interval excludes zero; a hollow marker means it does not. This carries the verdict without color.
  • Right-aligned numbers: the estimate and interval are printed in the row, so no one has to read values off the axis.
  • Axis label says what the number is: "Change against the baseline, in points (95% interval)", with "Candidate worse" and "Candidate better" at the ends.
  • No bar charts of averages. A bar hides the interval.
  • Table alternative: every chart has a data table behind a "View as table" toggle, and the chart has a text summary for screen readers (section 9).
  • Small samples: slices with fewer than 30 cases show their interval and a warning, and are excluded from any summary verdict.
  • Cost against quality (Phase 3): a Pareto scatter, with the frontier drawn and dominated candidates dimmed. Axes always start at a meaningful value, not at zero by default.

Each component has anatomy, states, keyboard behavior and an accessible name. Components are built on accessible primitives (menus, dialogs, tabs, popovers) so focus and roles are correct by default, and they are documented with a visual and an accessibility test in the component library.

5.2 Badges: aliases, modes, verdicts and status#

  • Aliases use weight, not color, to show how protected they are: dev is outlined, staging has a heavier outline, prod is solid ink.
  • Run modes appear next to every in-workflow result (UX-020): live is solid, replay is hatched with a clock icon, fork has a heavy left edge with a branch icon. Each has a text label.
  • Verdict pills pair a trend icon, a word and a tint. The words are fixed: Better, Worse, Inconclusive. "Guardrail failed" is a separate warning pill that can sit beside any verdict.
  • Status uses an icon and a word; only Failed uses color.

5.3 Feedback: alerts, toasts and dialogs#

  • Inline alerts sit where the problem is and stay until it is fixed. They have a plain sentence, then actions.
  • Toasts confirm an action that completed and offer one follow-up: Undo or View. They last 8 seconds, pause on hover and focus, and never carry an error that needs a decision.
  • Dialogs are used only for protected actions: moving an alias, running live against a service that writes, deleting data, rotating a key. They state the effect and the scale, require a typed confirmation for production aliases, and return focus to the trigger when closed.

5.4 Data: interval plot, tables and run progress#

Tables are the main way to read items, prompts and runs. They stay readable with 10,000 rows because the body is virtualized. Header rows stay in view. Column widths persist per user. Sorting and filtering are in the URL. Rows that need attention (regressions, failed checks, divergences) are sorted first or marked, never buried.

5.5 Command palette#

The palette searches names, ids and tags across areas, ranks recent items first, and runs actions. Every action in the palette is also in the UI and in the CLI, so the palette is a shortcut and never the only way.

6.2 Prompt library (UX-001)#

  1. Search covers names, text and tags, and / focuses it from anywhere. Filters show as removable chips, and saved views sit above the table.
  2. Alias chips show where each version is live. Weight, not color, marks how protected an alias is, so prod stands out without a red or green signal.
  3. The latest experiment's verdict is on the row, so a lead can see which prompts have a candidate waiting. A running experiment shows its progress inline.
  4. The selected row has a heavy left edge. Row actions (open, playground, new experiment, copy link) appear at the right on hover and focus, and are reachable by keyboard.

6.3 Prompt editor (UX-002)#

  1. An undeclared variable is caught as you type, with the line, the name and two ways out: declare it or remove the braces. Saving is blocked until it is resolved, because an undeclared name would reach the model as literal text.
  2. A change note is required to save. The error appears after the first attempt, not on load. The saved note shows in history, approvals and the library.

The editor shows the prompt exactly as the model receives it, including a token count. The right panel holds variables, model and parameters, the output schema, and history. Drafts autosave every few seconds and survive reload; a draft is private until it is saved as a version. If another person saves while you are editing, you are offered a side-by-side merge, never a silent overwrite.

6.4 Version history and comparison (UX-005)#

Comparison covers text, variables, output schema, and model with parameters, each with a count of changes. A parameter change gets its own warning, because a lower temperature can change results as much as a rewritten sentence. Restoring an old version creates a new draft; history is never rewritten.

6.5 Playground (UX-003, UX-004)#

  1. The inputs form is generated from the variable schema, so a reviewer fills in fields instead of editing JSON. Load a saved test case, or paste a real input.
  2. Up to four models run side by side. Words that differ from the first column are marked with an underline and a tint, so differences are visible without reading every line.

Streaming output appears as it arrives. Each column reports whether the output matches the schema, its token count, cost and latency. "Save as test case" keeps the inputs and the chosen answer as the expected output. "Open as experiment" carries the prompt, inputs and models into the builder.

6.6 Experiment builder (UX-007)#

  1. Where to run it is the central choice. Prompt alone tests the prompt in isolation. In workflow, replay upstream tests it inside the service and replays earlier steps from captures. Whole workflow runs everything live. The panel says what will replay, what will run, and that writes are blocked.
  2. The estimate updates as you choose. Trials, live model calls, cost range, time and power appear before anything runs, with a budget cap that stops the run when reached. The YAML switch shows the same experiment as a file for version control.

6.7 Results summary (UX-009, UX-011, UX-020)#

This is the screen the product is built around.

  1. The verdict is a sentence, not a score: which variant, better or worse at what, by how much, with the interval and the number of cases. A lead can repeat it to someone else.
  2. The evidence strip states how the numbers were made: mode, replay fidelity, capture age, dataset version and row count, the judge and how well it agrees with humans, and cost. Replay results can never look like live ones (UX-020).
  3. Guardrails are listed separately from the quality metric, with pass or fail and the limit. A variant that wins on quality and fails a guardrail shows both facts without averaging them.
  4. Slices warn when they are too small. A breakdown by tag shows its interval and a warning under 30 cases, and excludes that slice from the verdict.

Beneath the plot, "View as table" shows every number, and a footer lists the statistical method, the confidence level, the correction for several comparisons, and the equivalence band in use. These are readable by everyone and editable only when creating an experiment.

6.8 Results detail (UX-010)#

  1. Regressions come first by default. The sort and the tag filter are in the URL. The summary line counts regressions, improvements and unchanged cases.
  2. The judge's rationale sits beside the outputs, with the expected answer from the gold set. A reviewer can disagree with a judge from this panel, and that disagreement feeds judge calibration.

6.9 Trace diff (UX-017, UX-019, UX-020)#

  1. Steps served from a capture are hatched; steps that ran live are solid. The legend is always visible. A replayed step shows how many rows it read, so a reviewer can see the data was real.
  2. The first divergence is marked and its output is shown for both runs. Everything above it is identical by construction, which tells a developer where to look.

6.10 Connect a workflow (UX-014, UX-015, UX-016)#

  1. A failed check says what is wrong and how to fix it, with the exact command to copy. Experiments on the service stay blocked until every check passes; prompt-only tests keep working.
  2. The call-site map lists every agent or node PromptLab found, with its prompt and the number of tunables, each linked to the registry. A missing agent is visible immediately.

6.11 Approvals (UX-013)#

  1. The decision is possible on one screen: verdict sentence, interval plot, evidence strip, the prompt diff, and the checks. The lead should never need to open another tab to decide.
  2. "What this changes" states the blast radius: which alias moves, how much traffic uses it, whether other workflows share the prompt, and that rollback is one click.

Approving moves the alias and shows a toast with Undo for a short time; after that, rollback is in history. The approver cannot be the author unless the workspace policy allows it, and when it does not, the screen says so instead of hiding the button.

6.12 Phone views (UX-102)#

On a phone, results and approvals are fully readable and decidable. Editing, building and connecting open in read-only view with a clear notice, because those tasks need a keyboard and a wide screen. Action bars dock to the bottom with 40 px targets, and the verdict comes first.

6.13 Screens specified in text#

Datasets (UX-006, Phase 2). Datasets are small, typically 10 to 20 rows. Three ways in: pick rows from the read replica by table or SELECT query (preview and total count shown; a query returning more than 200 rows asks the user to narrow it), type a single input in a form generated from the workflow’s input format, or paste comma-separated values, one row per line. Columns map to the workflow’s input fields with suggestions from the identified format; rows can be edited, added or removed, and errors are marked per row. There are no train, validation or test splits. Each experiment keeps a snapshot of the rows it used. Empty state: type one input or paste a few rows.

Human review (UX-012). One pair at a time, filling the screen. Output A and output B are shuffled and unlabeled, with the rubric in a collapsible panel and the expected answer hidden unless the rubric asks for it. Keys: 1 for A, 2 for B, 3 for tie, U to undo, and arrow keys for next and previous. A progress bar shows pairs done and time spent. Leads see reviewer agreement and which items reviewers disagreed on.

Captured inputs (UX-018). A table of traces for one call site, with filters for date, outcome and tag. Selecting rows opens a redaction preview that shows exactly what will be masked, by rule, before anything is saved. A final step names the dataset and shows how many cases remain after redaction and de-duplication.

Optimization (UX-021). A candidate table with lineage (parent, generation, change summary), a Pareto scatter of quality against cost with the frontier drawn, and a diff against the parent for the selected candidate. Candidates outside the frontier are dimmed. A banner states that candidates are scored on rows the optimizer used and become activatable only after confirmation on rows it never saw.

Admin (UX-022). Tabs for providers and keys (secret values never shown after saving, only last four characters and rotation date), roles (a matrix of permissions by role), budgets (per team and per experiment, with alert thresholds), retention (per data type, with the date it takes effect), and the audit log (searchable by actor, action and object, exportable).

7.3 Long-running work (UX-106)#

Experiments, captures, optimizations and large uploads run on the server, not in the tab. Starting one returns immediately with a run page. Progress is by variant, with cases done, spend against budget, and an estimate of time left, and it survives reload and device change because it is stored with the run. The run page streams updates; if the stream drops, it falls back to polling without any visible change. A finished run notifies the person who started it. Pause, resume and cancel are always available and say what will happen to work in flight.

8.2 Behavior rules#

  • Autosave and drafts: edits to prompts and experiment drafts save automatically and are private until published as a version or started.
  • Concurrency: saves carry a version token. A conflict opens a side-by-side merge; nothing is overwritten silently.
  • Undo: destructive or hard-to-reverse actions offer Undo in a toast for 8 seconds; alias moves also have rollback in history.
  • Selection and bulk actions: selecting rows shows a bar with the count and actions; actions that change state show what they will affect before they run.
  • Live updates: running experiments update in place. New rows do not move the row the person is reading; a "3 new results" chip lets them catch up.
  • Copy as CLI and API (UX-107): every action that creates or runs something has a menu entry that copies the equivalent command or request, with the current values filled in and secrets left as references.
  • Validation: inline, after blur, with specific messages. A form with errors puts focus on the first error and announces the count.
  • Confirmations: only for protected, costly or irreversible actions. Routine actions never ask.
  • Persisted preferences: theme, density, column widths, last filters and shortcut settings, stored per user.

11. Content design#

11.1 Voice#

Plain, direct and specific. Sentence case everywhere. Active voice. Say what happened and what to do. No exclamation marks, no humor in errors, no apology. A button says exactly what it does, and the same action keeps the same name in the button, the toast and the history ("Publish", then "Published").

11.3 Writing patterns#

  • Verdict line: "{variant} is {better, worse} than {baseline} at {metric}: {delta} points (95 percent interval {low} to {high}) across {n} paired cases." For inconclusive: "{variant} shows no clear difference from {baseline} at {metric}: {delta} points (95 percent interval {low} to {high}), {n} cases."
  • Empty state: what this is, why it matters, one action that starts it, and a sample to try.
  • Error: what happened, where, what to do. Technical detail on request.
  • Confirmation: the effect and the scale ("About 3,400 requests a day will use v14"), then the verb on the button ("Move prod alias").
  • Numbers: tabular figures; percentages and points are not mixed in one column; deltas always show a sign; currency has two decimals under $100; intervals use "to", not a dash.
  • Dates: relative for under a week ("2 hours ago") with the full timestamp on hover; absolute after that.
  • Localization: all strings externalized from day one, no concatenated sentences, plurals handled by the message format, and layouts that tolerate 40 percent longer text. English first; right-to-left is not a Phase 0 to 3 target, and the layouts use logical properties so it can be added.

12. Frontend architecture and performance#

12.1 Recommended stack#

  • Language and framework: TypeScript and React, with a typed client generated from the same OpenAPI document that defines the backend contract, so screens and API cannot drift.
  • Routing and data: a router with typed search parameters (the URL is the source of truth for filters, sorting and selection) and a query cache for server state. Local state stays local.
  • Components: accessible headless primitives for menus, dialogs, tabs and popovers, styled with tokens. Tokens are authored once as data and compiled to CSS variables and TypeScript types, with light and dark themes.
  • Editor: a code-editor component that supports custom decorations (variable highlighting, undeclared-variable errors), diff, and accessibility, rather than a plain textarea.
  • Tables: a headless table with row virtualization.
  • Charts: purpose-built SVG for the interval plot and trace timeline (small and fully controllable), and a light canvas library only for the Phase 3 scatter.
  • Realtime: server-sent events for run progress with automatic fallback to polling.
  • Feature flags: the same OpenFeature-compatible resolution used by the backend, so a screen can ship dark behind a flag.
  • Observability: browser traces and errors reported with the same trace context as the backend, with no prompt text, outputs or inputs in any telemetry.

How to read this#

Capability levels. What PromptLab can do with a service depends only on how close it can get to the model calls, not on the shape of the API.

Level Requires PromptLab can
Full The process that calls the model runs under promptlab run (Python ADK, LangGraph, LangChain, or plain Google GenAI) Observe, steer prompts, templates, tool descriptions and parameters, memoize, capture data reads, fork from any step, score each step
Gateway The model client’s base URL points at the PromptLab gateway (any language) Observe model calls, steer static prompts and parameters, memoize model calls; capture data reads only where an OpenTelemetry agent instruments the service
Black box Only the API is reachable Run datasets, score outputs, compare versions or configurations of the service; no prompt overrides

The one rule. An interaction pattern never lowers the level by itself. What matters is whether PromptLab’s run context (the W3C traceparent and baggage headers carrying run id, overlay and mode) reaches the process that makes the model calls. Synchronous HTTP carries it automatically. Async jobs, webhooks, queues and background workers must forward it, in the job record or the message attributes. promptlab doctor checks this with a canary overlay, and each case below says how context travels.

K6 in code: ADK review loop#

from google.adk.agents import LlmAgent, LoopAgent
from google.adk.tools.tool_context import ToolContext

def approve_draft(tool_context: ToolContext) -> dict:
    """Call only when the draft meets every review criterion. Ends the review loop."""
    tool_context.actions.escalate = True
    return {}

writer = LlmAgent(name="writer", model=MODEL, output_key="draft",
    instruction="Write or revise the policy summary for {topic}. Reviewer feedback so far: {feedback?}")
critic = LlmAgent(name="critic", model=MODEL, output_key="feedback", tools=[approve_draft],
    instruction="Review this draft against the style guide:\n{draft}\n"
                "If it passes every check, call approve_draft. Otherwise list the fixes.")
review_loop = LoopAgent(name="review_loop", sub_agents=[writer, critic], max_iterations=3)

PromptLab sees agent:writer/llm and agent:critic/llm, counts iterations from the trace, and can score quality against cost per extra loop.

G3 in code: LangGraph router and branches#

python
from typing import Literal
from pydantic import BaseModel

class Route(BaseModel):
    route: Literal["billing", "tech", "other"]

ROUTER = pl.prompt("support.router", default="Classify this request: {message}", variables=["message"])
router_llm = llm.with_structured_output(Route)

def route(state: State):
    return {"route": router_llm.invoke(ROUTER.render(message=state["message"])).route}

builder.add_node("route", route)
builder.add_conditional_edges("route", lambda s: s["route"],
                              {"billing": "billing", "tech": "tech", "other": "fallback"})

Changing only the billing branch’s prompt replays the router from cache; changing the router reruns everything after it.

G7 in code: LangGraph map-reduce#

python
import operator
from typing import Annotated, TypedDict
from langgraph.types import Send

class State(TypedDict):
    docs: list[dict]
    summaries: Annotated[list, operator.add]
    report: str

def fan_out(state: State):
    return [Send("summarize_doc", {"doc": d}) for d in sorted(state["docs"], key=lambda d: d["id"])]

def reduce(state: State):
    parts = sorted(state["summaries"], key=lambda s: s["doc_id"])      # deterministic reduce prompt
    return {"report": llm.invoke(REDUCE.render(parts=parts)).content}

# refund_service/app.py
import json, os, uuid
from datetime import date
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from google.genai import types
from google.adk.runners import Runner
from google.adk.sessions import DatabaseSessionService
from google.adk.agents.run_config import RunConfig, StreamingMode
from promptlab.adk import PromptLabPlugin           # proposed PromptLab plugin
from .agents import refund_pipeline
from .repos import customers_repo, decisions_repo, parse_decision

app = FastAPI(title="Refund assistant")
sessions = DatabaseSessionService(db_url=os.environ["SESSION_DB_URL"])
runner = Runner(agent=refund_pipeline, app_name="refund_service",
                session_service=sessions, plugins=[PromptLabPlugin()])

class AssistRequest(BaseModel):
    customerId: str
    message: str
    channel: str = "web"
    replyStyle: str = "friendly"
    requestTime: str | None = None      # injected clock; defaults to today
    dryRun: bool = False

def sse(event: str, data: dict) -> str:
    return f"event: {event}\ndata: {json.dumps(data)}\n\n"

@app.post("/v1/refunds/assist")
async def assist(req: AssistRequest):
    request_id = f"req-{uuid.uuid4().hex[:8]}"
    customer = customers_repo.get(req.customerId)
    session = await sessions.create_session(
        app_name="refund_service", user_id=req.customerId,
        state={"customer_id": req.customerId, "customer_tier": customer.tier,
               "channel": req.channel, "reply_style": req.replyStyle,
               "today": (req.requestTime or date.today().isoformat())[:10]})

    async def stream():
        yield sse("started", {"requestId": request_id})
        current = None
        async for event in runner.run_async(
                user_id=req.customerId, session_id=session.id,
                new_message=types.Content(role="user", parts=[types.Part(text=req.message)]),
                run_config=RunConfig(streaming_mode=StreamingMode.SSE)):
            if event.author != current:
                current = event.author
                yield sse("stage", {"agent": current})
            for call in event.get_function_calls():
                yield sse("tool", {"agent": event.author, "name": call.name})
            if event.author == "responder_agent" and event.partial and event.content:
                text = "".join(p.text or "" for p in event.content.parts)
                if text:
                    yield sse("delta", {"text": text})
        final = await sessions.get_session(app_name="refund_service",
                                           user_id=req.customerId, session_id=session.id)
        decision = parse_decision(final.state["decision"])      # validates the JSON, raises on bad shape
        writes = [{"table": "refund_decisions", "op": "insert", "key": request_id}]
        if not req.dryRun:
            decisions_repo.save(request_id, req.customerId, decision)   # the only write, idempotent
        yield sse("result", {"requestId": request_id, "decision": decision,
                             "reply": final.state["reply"], "intendedWrites": writes,
                             "dryRun": req.dryRun})

    return StreamingResponse(stream(), media_type="text/event-stream")

E3. One trial, step by step#

The API flow of a single trial: variant rules_v3, test case refund-0031, repetition 0, in FORK mode.

  1. Schedule. The experiment engine hands the trial to the runner gateway, interleaved with the baseline trial for the same case and repetition.
  2. Pre-run check. The fixtures (customer C-1029, order 8812) are confirmed on the replica through a read-only query.
  3. Request. The adapter renders the request body from the test case, adds traceparent and baggage (run id, overlay reference, mode FORK), and posts to /v1/refunds/assist with dryRun: true.
  4. Session. The service’s web-framework instrumentation extracts the context; the API creates the ADK session (in the writable test session store) with tier, channel, style and date, and starts the pipeline.
  5. Intake. The model plane finds no overlay entry for intake_agent; the request is identical to the baseline’s, so the memo cache answers (hit).
  6. Research, in parallel. The policy retriever’s model call, its embedding call and its vector query all hit; the account researcher’s model call and SQL reads hit too.
  7. Resolver. The overlay patches the instruction with template v3; the plugin fills {policy_context}, {account_facts}, {today} and {customer_tier}. The request differs, so it misses and goes live to Gemini. Its call to fraud_checker is a new request and runs live; get_refund_limits hits.
  8. Responder. Its input (the decision) changed, so it misses and runs live, streaming delta events to the adapter.
  9. Result. With dryRun, the API skips the write, lists the intended insert, and sends the final result event.
  10. Collect. The adapter extracts reply and decision fields, records time to first delta, and confirms that the applied overlay hash matches the requested one; otherwise the trial is invalid.
  11. Score. Spans arrive over OTLP; evaluators score the output and the steps (using the retrieved passages from the trace); the statistics engine pairs the score with the baseline trial for the same case and repetition.

    return {"draft": msg.content}

def critique(state: State):
    msg = llm.invoke([("system", CRITIQUE), ("user", state["draft"])])
    return {"reply": msg.content}

builder = StateGraph(State)
builder.add_node("retrieve", retrieve)
builder.add_node("draft", draft)
builder.add_node("critique", critique)
builder.add_edge(START, "retrieve")
builder.add_edge("retrieve", "draft")
builder.add_edge("draft", "critique")
builder.add_edge("critique", END)
graph = builder.compile()

A8. Errors and business outcomes in the body#

  error_message: "$.error.code"
  output: "$.answer"
  fields: {outcome: "$.status"}

A real failure is scored as a failure with its code; an expected refusal is scored against expected.outcome. Without this, a 200 error body would be scored as an empty answer.

B. Interaction patterns#

Each case ends with Context travels: how the run context reaches the process that calls the model. Helper names under pl.context are proposed PromptLab SDK functions.

B1. Submit, then poll#

A research-report pipeline that takes minutes. The API accepts the job, a worker runs the ADK agents, and a status endpoint returns the report.

text
POST /v1/reports {"accountId": "A-77", "topic": "churn risk"}   →   202 {"jobId": "j-41"}
GET  /v1/reports/j-41   →   {"status": "running"}   …   {"status": "done", "report": {"summary": "…", "sections": […]}}
yaml
request:
  method: POST
  path: /v1/reports
  body: {accountId: "{{ item.input.account_id }}", topic: "{{ item.input.topic }}"}
async:
  job_id: "$.jobId"
  poll: {path: "/v1/reports/{{ job_id }}", every_ms: 2000, until: "$.status in ['done', 'failed']", timeout_ms: 600000}
  failed_when: "$.status == 'failed'"
response:
  output: "$.report.summary"
  fields: {sections: "$.report.sections[*].title"}

Context travels on the job record: the API stores the incoming traceparent and baggage with the job, and the worker restores them before running the agents. OpenTelemetry instrumentation for common task queues (such as Celery) does this automatically; for a custom queue, call pl.context.inject(job.headers) when enqueuing and pl.context.attach(job.headers) in the worker.

C5. Service in another language#

A Java, Go or Node service calling a model through its own SDK or plain HTTP.

  • Steer and observe through the gateway: set the model client’s endpoint or base URL to the PromptLab gateway (most model SDKs and HTTP clients allow a custom endpoint). Add one header, X-PromptLab-Call-Site: triage.classify, for stable call-site names; otherwise the gateway names call sites by fingerprint.
  • Traces: OpenTelemetry’s language agents (for example the Java agent) trace inbound HTTP, outbound HTTP and JDBC with no code change, and propagate traceparent and baggage.
  • Limits: static prompts and parameters can be changed; templates with per-request values are best effort through template induction; data reads are traced but not captured for replay, so FORK replays model calls only.
  • The adapter is plain http-generic; nothing about the contract changes. ADK also ships in Java and Go, so native shims can follow if teams adopt them.

D. Safety and environment#

D1. Writes with no dry-run option#

A service that writes to Postgres on every request and has no dryRun flag. Against a read-only role, its write fails and the request may return an error, which hides the answer you wanted to score.

Option Phase How it works Trade-off
Disposable writable copy 1 The test deployment points at a database restored from a snapshot for each experiment Real writes, fully isolated; costs a restore per experiment
Write blocking in the I/O plane 2 Write statements become recorded no-ops, so the service carries on and responds normally No service change; the attempted write becomes a scored signal
Add a dry-run flag Any The team adds dryRun and returns intended writes (Workflow developer guide, section 4) A small code change; the clearest results

The production primary is never an option: doctor blocks experiments when the business database role can write.

D2. External side effects#

A service that sends email, opens tickets or calls a payments API. Outbound calls are classified like database writes, and per-host rules decide what happens outside LIVE mode:

yaml
effects:
  write: deny
  http:
    - match: {host: api.sendgrid.com, method: POST}
      action: mock                                  # the service gets a plausible success
      response: {status: 202, body: {}}
      record_as: email_sent                         # visible to evaluators
    - match: {host: tickets.internal, method: POST}
      action: mock
      response: {status: 201, body: {id: "T-TEST"}}
      record_as: ticket_opened
    - match: {host: payments.internal}
      action: block                                 # fail loudly; never mock money

Evaluators can then assert, for example, that exactly one email was attempted and that it went to the customer on file. LIVE tests use each provider’s sandbox endpoint instead.

D3. Service-side response cache#

A service that caches answers (in Redis, or a semantic cache keyed by similar questions) returns the baseline answer to every variant, so all variants look identical. This is a silent failure, and PromptLab catches it: no model call happens, so steer verification fails and the trials are marked invalid instead of scored.

The fix is to disable the cache in the test deployment, or to honor a bypass header that the adapter sends:

yaml
request:
  headers: {Cache-Control: no-cache, X-Bypass-Response-Cache: "true"}

D4. End-user authentication#

A service that requires an end-user token and behaves differently by role or tenant (an agent-assist tool where tier-2 agents may approve larger refunds).

yaml
auth:
  identity_from: "{{ item.context.identity }}"       # for example test-agent-tier2
  exchange:
    type: oauth_token_exchange
    token_url: https://idp.test.internal/oauth/token
    secret_ref: vault://promptlab/test-idp

Test identities exist only in the test identity provider, each with fixed claims. Datasets name identities, never tokens, and results can be sliced by role to show, for example, that a prompt change helps tier-1 agents but hurts tier-2.

D5. Slow or rate-limited service#

yaml
limits:
  concurrency: 4
  rate_per_minute: 60
  timeout_ms: 180000
  retry: {on_status: [429, 503], max: 3, backoff: exponential, honor_retry_after: true}

Retries cover transient failures only; a trial that still times out is a scored failure, never silently dropped. Because trials are interleaved across variants, a slow afternoon affects every variant equally, and latency guards compare variants within the same experiment.

Building AI workflows for PromptLab

How to write ADK and LangGraph workflows so PromptLab can test, compare and optimize their prompts with no special code. Each rule says why it matters, so teams keep their own style everywhere else.

1. The rules at a glance#

  1. Keep prompts as templates with named variables. Never assemble instructions by concatenating strings in code.
  2. Give every agent, node and prompt a stable, unique name. PromptLab’s call-site ids and history are built from them.
  3. Call models through supported clients, with the model id in configuration. A model upgrade then becomes a config change that can be tested.
  4. Ask for structured output wherever a later step or an evaluator reads the result.
  5. Read Postgres through standard drivers, with connection strings from configuration, and keep reads and writes in separate code paths.
  6. Make writes idempotent and put them in one place, ideally the last step of the workflow.
  7. Return structured API responses: the answer, the decision fields and a request id, at stable paths.
  8. Publish an OpenAPI document for every service.
  9. Start every service through the PromptLab launcher. It adds tracing and testability, and it fails open.
  10. Inject time and per-request data; never read the clock or globals while building a prompt.

Everything else (folder layout, frameworks for the API, coding style) is each team’s choice.

2. Prompts as data#

Why it matters: PromptLab can only test and swap a prompt it can see as a template. A prompt built by string concatenation is invisible as a unit: it cannot be versioned, diffed, edited with its variables kept, or optimized.

Rules

  • One prompt per model call site. If two branches need different instructions, use two prompts, or one prompt with a variable, not code that splices sentences together.
  • Stable ids in the form <workflow>.<agent or node>.<purpose>, for example refunds.assistant.system.
  • Instructions static, data in variables. Retrieved rows, user details and dates go in variables; the instruction text stays fixed.
  • Typed, documented variables. Each variable has a type and one line saying what fills it.
  • Few-shot examples as their own variable (a list), so they can be tuned separately.
  • No secrets or personal data written into templates.
  • Prompt text in files or the registry, not scattered through code: prompts/*.yaml beside the code works until runtime resolution is adopted.

Don’t

python
instruction = ("You are helping " + user.name + ". Today is " + str(datetime.now()) +
               ". " + load_rules() + (" Be brief." if channel == "sms" else ""))

Do (ADK template, values supplied through session state)

python
instruction = ("You are helping {user_name}. Today is {today}. "
               "Follow these refund rules:\n{refund_rules}\nReply style: {reply_style}.")

3. Model calls#

Why it matters: PromptLab steers and records prompts at the model client. Calls that bypass supported clients are not seen, and model ids buried in code make upgrade tests a code change.

  • Use supported clients. ADK calls Gemini through the Google GenAI client already. In LangGraph, create models with init_chat_model or the provider chat-model packages, which sit on the provider SDKs. A hand-written HTTP call to a model endpoint bypasses the interceptor; if one is unavoidable, send it through the PromptLab gateway URL.
  • Model ids and parameters in configuration, for example SUPPORT_MODEL=gemini-2.5-flash, with temperature and output limits set explicitly.
  • Structured output with a schema wherever the result is parsed: output_schema on an ADK LlmAgent, or with_structured_output on a LangChain chat model. Evaluators then score fields, not prose.
  • Let model errors surface. A swallowed error becomes a fake answer that scores as a success.
  • Keep calls on the request’s context. When work moves to threads or tasks, copy the context (contextvars.copy_context() in Python) so overlays and traces follow.

4. Data access and PostgreSQL#

Why it matters: your workflows read context from Postgres and write results to production. PromptLab must capture the reads (so tests use real context) and must never let a test reach the writes.

  • Use standard, instrumented drivers: psycopg 3, asyncpg or SQLAlchemy. Uncommon drivers or raw sockets are not captured.
  • Connection strings from configuration, with separate read and write settings (DATABASE_READ_URL, DATABASE_WRITE_URL). A test deployment then points at a replica or staging copy with a read-only role, with no code change.
  • Separate read and write paths. Put writes behind a small repository layer with explicit write methods, so they are easy to find, classify and block.
  • Writes idempotent, with a key derived from the request, so a retried or replayed run cannot double-apply.
  • Writes last. Compute the decision first and persist it in a final step. Tests can then score the decision even when the write is blocked.
  • Support a dry-run option in the service: skip writes and return the intended writes in the response. Tests can then score “would it have refunded the right order” in addition to write blocking.
  • Handle a refused write cleanly. In a test deployment the read-only role makes writes fail; return the decision with a clear error field instead of crashing.
  • Deterministic queries. Add ORDER BY to every query whose rows reach a prompt, and an explicit row limit. Unordered rows change the prompt from run to run, which causes flaky results and cache misses.
  • Retrieval settings in configuration. For pgvector or full-text retrieval, keep k, thresholds and filters in config so they can be tuned like prompts.

5. Service API contracts#

Any request and response shape works: PromptLab adapts to your contract with a mapping file. These conventions make that mapping short and the results scoreable.

6. ADK specifics#

  • Unique, stable agent names. Call-site ids are agent:<name>/llm. Renaming an agent splits its history, so treat a rename as a migration and record it.
  • Instructions as string templates with {state_variables}. ADK fills them from session state. Avoid computing the instruction in a Python function or by concatenation: the plugin then sees only rendered text and cannot edit the template safely. If a value must be computed, compute it into session state and keep the template static.
  • Per-request data in session state at session creation. This is exactly what the adk-api-server profile maps dataset fields into, so test items and real requests travel the same path.
  • Tools as plain functions with typed parameters and precise docstrings. The docstring becomes the tool description the model sees, which PromptLab can test and tune. Name read tools and write tools so their effect is obvious.
  • Descriptions for sub-agents. In multi-agent apps, each sub-agent’s description guides delegation and is itself a tunable.
  • Structured results through output_schema, and output_key to store an agent’s result in state for later agents.
  • Register PromptLabPlugin on the Runner in every environment. Run tests through a Runner or adk api_server; ADK plugins are not supported in the ADK web UI.
  • Model id from configuration.

Do

7. LangGraph specifics#

  • Unique, stable node names. Call-site ids are node:<name>.
  • One model call per node where practical, with one declared prompt. Declare templates with pl.prompt or keep them in prompt files; LangChain agents can use the PromptLab middleware instead.
  • Models from init_chat_model or provider chat-model packages, with the model id from configuration.
  • Typed state (TypedDict or Pydantic). Keep retrieved context in its own state key, so traces and evaluators can see what each prompt was given.
  • Deterministic routing. Conditional edges decide from structured outputs or state, never from randomness or free text parsing.
  • Writes in a dedicated final node (for example persist). FORK runs then block one clearly marked step, and evaluators can read the intended write from state.
  • Request fields mapped into initial state explicitly when the graph sits behind your own API, so the adapter’s fields and real requests follow one path.
  • Checkpointer optional. PromptLab forks through its memo cache and does not need one; keep it if your workflow needs human-in-the-loop resumes.

Do

python
import os
from typing import TypedDict
import promptlab as pl
from langgraph.graph import StateGraph, START, END
from langchain.chat_models import init_chat_model

llm = init_chat_model(os.environ.get("REPLY_MODEL", "openai:gpt-4.1-mini"))

DRAFT = pl.prompt("replies.draft.system",
    default="Write a reply to the customer.\nAccount history:\n{history}\nMessage:\n{message}",
    variables=["history", "message"])

class State(TypedDict):
    message: str
    customer_id: str
    history: str
    reply: str

def retrieve(state: State):
    rows = notes_repo.recent(state["customer_id"], limit=20)   # ORDER BY created_at DESC inside
    return {"history": "\n".join(r.note for r in rows)}

def draft(state: State):
    return {"reply": llm.invoke(DRAFT.render(history=state["history"],
                                             message=state["message"])).content}

def persist(state: State):
    replies_repo.save(state["customer_id"], state["reply"])    # the only write, last
    return {}

builder = StateGraph(State)
for name, fn in [("retrieve", retrieve), ("draft", draft), ("persist", persist)]:
    builder.add_node(name, fn)
builder.add_edge(START, "retrieve")
builder.add_edge("retrieve", "draft")
builder.add_edge("draft", "persist")
builder.add_edge("persist", END)
graph = builder.compile()

Don’t: one node that queries the database, builds the prompt with f-strings, calls the model and writes the result. It cannot be forked, its prompt cannot be edited as a template, and its write cannot be isolated.

8. Determinism, observability and deployment#

Determinism. Identical inputs should produce identical prompts. That keeps tests stable and lets the memo cache reuse unchanged steps.

  • Inject the clock: pass “now” in the request or state instead of calling the clock while building a prompt.
  • Stable ordering: ORDER BY in queries, and sorted keys when serializing lists or dicts into a prompt.
  • No random ids in prompts. If one is unavoidable, add it to the volatile masks in promptlab.yaml.
  • Retries through library settings, never a loop that silently changes the prompt and tries again.

Observability

  • Logs include the trace id, so a log line and its PromptLab trace link up.
  • Background work (task queues, thread pools) carries the request context; prefer instrumented task libraries or copy the context explicitly.
  • Redaction rules for personal fields are declared in promptlab.yaml and applied before anything leaves the service.

Deployment

dockerfile
# Same image in every environment; the launcher fails open if PromptLab is unreachable
ENTRYPOINT ["promptlab", "run", "--"]
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8080"]
  • Every service has a test deployment: same image, PROMPTLAB_ENV=test, database settings pointing at a replica or staging copy through a read-only role.
  • API gateways in front of services pass traceparent and baggage headers through unchanged.
  • /version reports the deployed git commit, and /health reports readiness.
